### 2.2 `packages/engine` (`@bricklap/engine`)

- Ficheiros: `src/index.ts` (barrel), `types.ts`, `engine.ts`, `geo.ts`, `seed.ts`; `test/` com 8 ficheiros de teste (+ `helpers.ts`).
- Alterações à API (todas retrocompatíveis para o lab): `GpsCoords` estrutural em vez de `GeolocationCoordinates` (DOM); `stepSim(..., rng?)`; `createLiveSession(sport, at?, id?)`; `formatClock`/`formatDay` com `locale?`; novos `samplesForSegment`, `samplesBetween`, `interpolateAt`, `isLive`, `recoverLiveSessions`; constantes `MAX_PLAUSIBLE_SPEED_MPS` (55) e `RECOVERED_DEDUPE_MS` (2000).
- Defeito encontrado pelos testes e corrigido: o `seed.ts` calculava o fim de cada perna a partir do relógio de amostras (que deriva até 8 s por perna), pelo que as últimas amostras da sessão "brick" ficavam 6 s **depois** do evento `stopped`. Agora as pernas são cumulativas desde o início.
- Defeitos encontrados pela revisão adversarial (§11) e corrigidos:
  - `formatPace` arredondava os segundos depois de separar os minutos e mostrava "4:60/km" para 299.6 s/km. Agora arredonda o total primeiro.
  - `formatDistance(999.5)` dava "1000 m"; passa a "1.00 km".
  - Com GPS real, o troço que atravessa uma mudança de desporto não pertencia a nenhum segmento (só amostras exatamente na fronteira eram partilhadas). `samplesBetween` interpola agora uma amostra na fronteira quando há amostras dos dois lados; a soma das distâncias dos segmentos iguala a da sessão para qualquer cadência (testado também com os seeds).
  - Coerência `status` vs eventos: `isLive` exige `status: "live"` e ausência de `stopped`; `applyStop` num status desatualizado só corrige o status, sem segundo evento; `sessionBounds` usa o último `stopped`, como `segmentsFromEvents`.
  - `applyChange` sem segmento aberto (sem `started`) já não cria um `sport_changed` órfão.
  - `stepSim` com `dt` negativo (relógio a andar para trás) já não anda para trás.
- Sem zustand, sem `localStorage`, sem DOM: verificado por grep no fecho. `vitest` e `typescript` declarados como `devDependencies` do pacote (hoisted pela raiz).

## 9. Correr a app no telemóvel Android a partir de WSL 2

Contexto: a app usa **expo-dev-client**. O telemóvel precisa de um APK de desenvolvimento construído a partir do projeto (o Expo Go não serve). Depois do APK instalado, as alterações a TypeScript chegam por Metro (`npm run dev:mobile`), sem reconstruir o nativo.

### Opção A — EAS Build (nuvem da Expo)

A partir de `apps/mobile`:

```bash
npx eas-cli@latest login
```

```bash
npx eas-cli@latest build:configure
```

```bash
npx eas-cli@latest build --platform android --profile development
```

O `eas.json` gerado deve ter o perfil `development` com `developmentClient: true`, `distribution: "internal"` e `android.buildType: "apk"`. No fim a Expo dá um link/QR; abre-se no telemóvel e instala-se o APK. Depois `npm run dev:mobile` na WSL e ler o QR na app (telemóvel e PC na mesma rede Wi-Fi; se a rede bloquear, `npx expo start --dev-client --tunnel`).

Prós:
- Zero instalação de Android SDK/JDK na WSL; funciona com o ambiente atual.
- Keystore gerido pela Expo.
- Build reprodutível na nuvem, reutilizável em CI e para partilhar APKs.
- Não depende de USB nem de usbipd.

Contras:
- Exige conta Expo e projeto EAS (`projectId` em `app.json`) — decisão do CTO.
- Fila e tempo de build na nuvem (minutos); o plano gratuito tem limite mensal e prioridade baixa.
- O código sobe para servidores da Expo (aceitável num protótipo; um terceiro a considerar quando houver dados reais).
- Cada alteração nativa (módulo novo, permissões) obriga a novo build na nuvem.

### Opção B — Build local na WSL 2 (Android SDK + adb)

Instalar na WSL: JDK 17 (`sudo apt install openjdk-17-jdk`), Android command-line tools + `sdkmanager "platform-tools" "platforms;android-3x" "build-tools;3x.0.0"` (versões exatas: as que o `expo prebuild` do SDK 57 pedir), `ANDROID_HOME` e `JAVA_HOME`. Depois, em `apps/mobile`:

```bash
npx expo run:android --device
```

Gera `android/` (ignorado pelo git), compila com Gradle e instala via `adb`. Para o `adb` da WSL ver o telemóvel:

1. **adb por Wi-Fi (recomendado, sem USB passthrough)** — Android 11+: Definições → Opções de programador → Depuração sem fios → Emparelhar com código. Na WSL:

```bash
adb pair IP:PORTA_DE_EMPARELHAMENTO
```

```bash
adb connect IP:PORTA
```

2. **USB via usbipd-win** — no Windows (PowerShell admin): `winget install --interactive --exact dorssel.usbipd-win`; depois `usbipd list`, `usbipd bind --busid <id>` e `usbipd attach --wsl --busid <id>`. Na WSL: `lsusb`, `adb devices`. Pode exigir regras udev. Enquanto anexado, o Windows não vê o telemóvel.

Prós:
- Ciclo rápido depois da primeira instalação (rebuild nativo em 1–3 min, sem fila).
- Sem conta nem custos externos; o código não sai da máquina.
- Necessário mais tarde de qualquer forma (logcat, perfis, módulos nativos).

Contras:
- Instalação pesada (SDK + JDK + Gradle: vários GB; primeiro build lento).
- WSL 2 não tem USB nativo; usbipd funciona mas é frágil (desanexa ao suspender, `bind` precisa de admin). O adb por Wi-Fi evita isto.
- Emulador Android dentro da WSL não é prático; se quiser emulador, corre-o no Windows e liga o adb da WSL ao do Windows.
- Keystore de debug local; para release é preciso keystore próprio.

### Recomendação

Para validar a Fase 1 no telemóvel esta semana: **Opção A (EAS Build) para o primeiro APK** — menos atrito a partir da WSL. Preparar em paralelo a **Opção B com adb por Wi-Fi** para a Fase 2 (GPS real, foreground service), quando o ciclo nativo local compensa.

Alternativa sem nuvem: build no Windows (Android Studio) com o repo em `\\wsl$` é possível mas lento (I/O entre sistemas de ficheiros); não recomendado.
